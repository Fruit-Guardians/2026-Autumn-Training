# 二、学习并深入了解Patch

## 什么是Patch

Patch，就是修改程序二进制（机器码）里的指令或者数据，改变程序原本的运行行为，俗称 “打补丁”。

## 在 CTF 逆向场景里，Patch 的核心目的：

不找正确密钥 /flag，直接修改程序逻辑，绕过校验

1. 绕过校验逻辑，不用破解算法

很多逆向题里程序会校验密码、key、输入内容。

如果正向分析加密算法、推导正确答案很麻烦，我们可以直接 Patch 修改跳转指令，跳过验证，直接走向成功分支，快速拿到 flag。

例子：原本密码错就跳失败 → Patch 后不管输入什么，都跳成功。

2. 去除干扰代码（NOP 掉垃圾指令、花指令）

有些程序加了花指令、反调试代码，干扰我们逆向分析。我们可以把这些干扰指令nop掉，让程序逻辑变干净，方便后续分析。

3. 修改判定条件

直接修改程序里的比较数值，改变判断标准，让原本不满足的条件变成满足。

- 我对于Re文档中的疑问点

文档中改条件跳转举出的例子是从等于条件下跳转jz success到不等于条件下跳转jnz success，这里修改的是汇编代码，但是patch的定义是指在修改机器码，这是为什么：​

原因在于汇编是机器码的助记符号，IDA、x64dbg 会把二进制机器码翻译成汇编方便我们阅读。我们在图形界面选择修改汇编指令，只是工具提供的可视化操作方式；底层本质依旧是修改程序文件中的二进制机器码。

4. 调试、验证猜想

逆向分析时，我们猜测某段代码的作用，直接 Patch 修改二进制，运行测试，快速验证自己的分析猜想，不用重写源码。

## 怎么在IDA中操作Patch

### 1：找到目标指令

在反汇编窗口，定位到要修改的那一行汇编（比如 jz success），光标放在这条指令上。

### 2：两种修改方式（二选一）

1\.Assemble（直接写汇编）

Edit → Patch program → Assemble\.\.\.

在弹窗里输入新汇编，例如把 jz 改成 jnz，IDA 会自动翻译成对应的机器码。

·注意：新指令长度不能超过原来指令占用的字节，不然会破坏后面代码。也尽量不要更短（除非用到代码洞穴:把新增逻辑写到程序里一块空闲空白区域，在原位置放一条 jmp 跳过去执行，执行完再 jmp 跳回来。）,否则会留出多余字节，也会造成指令错位。

2\.Change byte（直接改二进制字节，更底层）

Edit → Patch program → Change byte\.\.\.

直接修改十六进制机器码，比如 jz 是 0x74，改成 0x75 就变成 jnz；改成 0x90就是 nop。

Keypatch 插件

# 三\.学习花指令

## 什么是花指令

花指令是为了干扰反汇编、反编译或人工阅读而插入的无效、冗余或误导性指令，实质就是一串垃圾指令，它与程序本身的功能无关，并不影响程序本身的逻辑。程序跑起来不受影响，但是静态看汇编的时候，IDA 很容易解析错乱、F5 反编译失败。在软件保护中，花指令被作为一种手段来增加静态分析的难度，花指令也可以被用在病毒或木马上，通过加入花指令改变程序的特征码，躲避杀软的扫描，从而达到免杀的目的。

## 花指令的分类

花指令一般被分为两类，被执行的和不会被执行的。

### 花指令之所以可以干扰到反汇编

反汇编算法主要可以分为俩类：递归下降算法和线性 扫描算法。

1）线性扫描算法

线性扫描算法p1从程序的入口点开始反汇编，然后对整个代码段进行扫描，反汇编扫描过程中所遇到的每条指令。线性扫描算法的缺点在于在冯诺依曼体系结构下，无法区分数据与代码，从而导致将代码段中嵌入的数据误解释为指令的操作码，以致最后得到错误的反汇编结果。

2）递归下降算法

递归下降采取另外一种不同的方法来定位指令。递归下降算法强调控制流的概念。控制流根据一条指令是否被另一条指令引用来决定是否对其进行反汇编，遇到非控制转移指令时顺序进行反汇编，而遇到控制转移指令时则从转移地址处开始进行反汇编。通过构造必然条件或者互补条件，使得反汇编出错。

### 不被执行的花指令

这类花指令通常形式为在代码中出现了类似数据的代码，或者IDA反汇编后为JUMPOUT\(xxxx\)（他是反汇编后得到的伪代码，IDA 识别到一条间接跳转（查表跳转，switch 分支），但是它暂时没自动解析出来这个跳转表，不知道会跳到哪一个分支，所以用 JUMPOUT\(\) 标记在这里。）\.

这类花指令一般不属于CPU可以识别的操作码，那么就需要在上面用跳转跳过这些花指令才能保证程序的正常运行。

#### 不被执行的花指令的作用形式

##### 首先我需要了解什么是静态运行和动态运行

IDA 静态按顺序解析字节，发生在把 exe 丢进 IDA，IDA 自动分析、自动反汇编的那一刻，也就是静态分析阶段，程序根本没有跑起来

举个例子：

jmp ok：靠一条能跑的 jmp，保护后面一串不跑的垃圾字节，用来骗 IDA

db 0x90,0x90

ok:

mov eax,1

- 对于静态分析而言，静态分析的时候，顺序解析字节

程序**没有运行**，只是一个躺在磁盘上的 exe 文件。 IDA 读取这个文件里的机器码，**从前往后一个字节一个字节尝试拆成汇编指令**。 它不会像 CPU 一样真的去执行 `jmp`、跟着跳转跑。所以遇到这个例子中的情况时，IDA 老老实实往下扫，扫完 jmp ok，继续往下读后面那两个 0x90，尝试把它们翻译成指令，就被花指令骗了。

- 对于动态分析（CPU 执行的时候）而言，

在这个例子中，双击 exe，或者在调试器里 F9 运行程序。

CPU 读到 jmp ok，直接跳去 ok 标签，跳过那两个 0x90，不去执行它们。

##### 两种不被执行的花指令形式如下

###### 如果我们插入的花指令是一个操作码，那么后面程序原本的机器码就会被误认为是这个操作码的操作数，从而导致反汇编引擎的解析错误。

###### 文中举出的例子：

int main\(\)

\_asm \{

xor eax, eax;异或操作，把 eax 清零，执行完 eax = 0。标志位 ZF（零标志）会被置 1。ZF=1 代表运算结果是 0。

jz s;如果 ZF=1，就跳转到标签s

\_emit 0x11;

\_emit 0x22;

\_emit 0x33;//0x33是xor指令的操作码，会导致后面正常的Push指令被错误解析

\_emit 的作用：直接往机器码里写入原始字节，不编译成汇编指令。

s:因为上面的 jz 直接跳走了，CPU 永远不会执行这三个字节

CPU 直接跳到s:的位置，跳过这一串。s只是一个标签，没有指令，继续往下走，执行 printf，正常输出 Hello World

\}

printf\("Hello World\!\\n"\);

\}

- 动态分析（CPU）视角：

程序完全正常，打印 Hello World；0x11,0x22,0x33 这三个字节躺在代码段里，但是永远不会交给 CPU 译码执行

- 静态分析视角（IDA中反汇编）视角：

IDA 静态分析不会模拟运行，不会自动提前判断 jz 会不会跳，它是从前往后逐个字节依次拆解指令：

IDA 读取顺序：

xor eax,eax → jz s → 下一个字节 0x11

IDA 不知道这里有跳转，后面这三个字节要跳过。

它会继续把 0x11 当成一条指令的开头，开始解析。

注释里说了：0x33 是 xor 的操作码。

IDA 从这几个乱字节开始错误译码，指令边界直接错位。

错位之后，后面原本正常的代码（包括 printf 相关的调用、push 等指令）全部被 IDA 认错、拆错。

- 结果：

反汇编乱掉

F5 伪代码出错

交叉引用丢失（能输出 Hello World，但是字符串交叉引用找不到）

- 解决方案

花指令骗的是静态分析工具（IDA），很难骗动态调试器（OD）。在加了这类花指令的情况下，我们想要定位关键函数只能借助动态调试的方法，首先在OD的内存窗口中搜索到Hello World字符串。\(p\.s:可能会出现多个相同的字符串，在C语言中常量字符串会被存放在rdata段，所以可以在这个范围内进行字符串的查找\)，然后在该地址设置内存访问断点（只要 CPU 读 / 写这块内存里面的数据，就断下来，不管是哪一行代码触发的），运行程序后使用快捷键ctrl\+F9进行堆栈回溯（顺着栈里面存的返回地址，往回查：是谁调用了当前这个函数，一层一层往上找出调用链。），即可定位到关键位置

###### 插入的花指令也可以是改变堆栈平衡的汇编代码，跟形式一相同在这些花指令上面写上跳转指令，虽然花指令不会被执行，但是IDA进行解析时会认为该函数堆栈不平衡，从而使F5功能失效

- 其中，我需要了解什么是栈平衡

栈可以理解为程序调用函数时使用的临时记事本，栈指针标记记事本当前顶端位置。

调用函数时，会把参数、返回地址依次放到栈上。按照约定，需要由调用者或者被调用函数，在函数执行结束后，把栈清理干净，让栈指针回到调用函数之前的位置。

如果清理的字节数量不对、或者忘记清理，栈指针无法复原，就是栈不平衡。

栈不平衡会导致 CPU 读到错误的返回地址，程序崩溃；同时 IDA 的栈分析失败，无法正常生成伪代码。

堆是独立的内存区域，不存在平衡这个概念。

###### 文中举出的例子：

int main\(\)

\{

\_asm \{

xor eax, eax;

jz s;

add esp, 0x11;这里就是改变栈平衡的花指令，只对静态分析时起作用，在CPU中运行时正常跳过花指令正常跳到s标签输出Hello World\!

s:

\}

printf\("Hello World\!\\n"\);

\}

- 动态分析视角（CPU运行过程）

1. xor eax, eax;

把 eax 清零，运算结果为 0，零标志位 ZF = 1。

2. jz s;

jz：ZF=1 就跳转。现在 ZF=1，一定会跳转到标签 s。

关键：add esp, 0x11; 这一行，CPU永远不会执行到，直接被跳过。

s: 只是标记位置，没有指令。往下走，执行 printf，正常打印 Hello World。

CPU 视角：程序功能完全正常，add esp,0x11 不会被执行。

- 静态分析视角（IDA进行反汇编时）

IDA 的扫描顺序：

xor eax,eax → jz s → 下一段就是 add esp,0x11 的机器码

IDA 不知道：这里的 jz 一定会跳走，后面这条指令是永远不会执行的诱饵。

IDA 会把 add esp,0x11 当成正常代码去解析，并且跟踪 esp（栈指针）的变化：

IDA 看到这条指令，会认为这里 esp \+= 0x11，栈指针发生了巨大改动。

于是 IDA 的栈分析（SP\-analysis）直接算错：

• 栈帧分析失败

• F5 伪代码错乱

• 后面 printf 的交叉引用、变量识别全部乱掉

- 解决方法

对抗方法同上，将造成堆栈不平衡的软件NOP掉即可。

### 会被执行的花指令

这类花指令本身是正常的汇编指令，它们运行完后不会改变原来程序的堆栈，寄存器，但能起到干扰静态分析的作用，一般分为两种，一种是改变堆栈操作，另一种是利用call指令或Jmp指令增加执行流程复杂度。

#### 会被执行的花指令的作用形式

##### 两种会被执行的花指令类型

###### 改变栈平衡操作类型

###### 文中举出的例子（改变栈堆操作）

IDA 静态分析时会逐指令跟踪栈指针 esp 的变化，中间这一次栈指针变动会干扰 IDA 的栈分析流程，可能造成伪代码、交叉引用解析异常，提升逆向难度。

int main\(\)

\{

\_asm \{

push eax;：把 eax 压栈 → esp \-= 4

add esp, 4;：esp \+=4，恢复回去

\}

printf\("Hello World\!\\n"\);

\}

执行完这两条花指令之后，所有寄存器、栈，和执行之前一模一样。没有任何改变，对程序功能一点影响都没有。

printf 照样正常输出 Hello World。CPU 跑的时候，这两句走一遍，啥效果都没有。

- CPU 视角：顺序执行 push eax、add esp,4，栈先减 4 再加 4，啥事没有，继续往下跑，printf 正常工作 

- IDA 视角：IDA 会跟踪 esp 的变化

- IDA 看到 push eax → esp\-4；然后看到 add esp,4 → esp\+4。

虽然最后栈是平衡的，但是中间产生了栈变化，很容易打乱 IDA 的栈分析（SP 分析），严重的时候：

1. IDA 栈分析报错

2. F5 反编译出来的伪代码错乱

3. 交叉引用识别异常

它没有跳转 \+ 垃圾字节，属于无作用等价指令花指令，是最简单的一类花指令。

- 解决方法

1. 直接在调试器里运行，用OD跟着 CPU 真实流程走

遇到jz s，观察标志位 ZF，直接跳转到s:，自动跳过后面诱饵指令。

2. 配合内存断点、堆栈回溯

在内存窗口找到 "Hello World\!\\n" 的地址，下内存访问断点，只要 CPU 读取这块字符串，调试器立刻停下。断下来之后栈回溯，直接找到 printf 的调用位置，跳回 main 里我们要分析的那段花指令代码。

###### 利用call指令来增加程序执行流程的复杂度

- 先回忆基础：

call xxx：自动把 call 的下一条指令地址压入栈，然后跳转到 xxx

ret：从栈顶弹出一个地址，跳过去

###### 文中举出的例子

- 核心代码：

call  40200B\#第一步：把call 后面那条指令的地址（也就是 add esp,0x17 的地址 0x40200B）压进栈

add esp,0x17   ; \#这一行就是call所在的下一行

ret \#ret 会弹出栈顶刚才存的返回地址 0x40200B，正常情况就跳回 add esp,0x17

- 关键花招：在 ret 之前，修改栈上这个返回地址

给栈里的返回地址 \+0x17

原来返回地址：0x40200B

修改之后：0x40200B \+ 0x17 = 0x402022

于是 ret 不再跳回 add esp,0x17，而是直接跳到 0x402022，跳过了中间一大片代码

- CPU 视角（动态运行）

整条 call → ret 这一串指令全部都会被 CPU 执行，不是像之前 jz 那种 “有一部分字节被跳过不跑”。

只是它偷偷修改栈上的返回地址，改变 ret 跳转目标，跳过中间代码。

程序逻辑正常，不会崩溃。

- IDA 静态视角（为什么会乱）

IDA 静态分析是按顺序逐行解析：

1. IDA 看到 call，默认理解：call 跑完，一定会回来执行 call 后面的 add esp,0x17

2. IDA 不知道：代码内部会修改栈上的返回地址，ret 不会回来！

IDA 会认为：add esp,0x17 是正常会执行的代码，继续跟踪 esp、分析后续指令。

实际 CPU 根本不会回来跑这一段，于是：

• 控制流分析错乱

• 函数调用图、交叉引用全部出错

• F5 伪代码乱成一团

- 解决方法

像这种花指令在程序中多次出现，但是他们都有相似的特征，靠手动清除需要耗费大量的时间，所以可以通过编写脚本来清楚这些花指令。
