## 一、什么是 SQL 注入
### 原理
后端 PHP 程序，**直接把用户输入的内容拼进 SQL 语句里执行**，没有做过滤或者转义。攻击者可以构造特殊输入，**修改原本 SQL 语句的逻辑**，从而读取、修改数据库里的数据。

>    
正常网站是 “用户输入 = 一段文字”；  
注入漏洞下，网站把 “用户输入” 当成**SQL 代码**去执行。  
就像本来只让你写名字，结果你写了一段指令，服务器直接执行了你写的指令。  
核心一句话：**数据和代码没有分开**。
>

举个简单例子：  
后端原始代码：后端原始代码：

```plain
$sql = "select * from users where id='".$get['id']."'";
```

正常访问：`?id=1`  
拼接后 SQL：`select * from users where id='1'`

注入 payload：`?id=1' or 1=1 #`  
拼接后 SQL：`select * from users where id='1' or 1=1 #'`

+ `'`：闭合前面的单引号，跳出字符串
+ `or 1=1`：永真条件，查询所有数据
+ `#`：注释掉后面剩下的单引号，避免语法报错

## 二、前置基础知识点
1. MySQL 基础
+ `select` 查询数据；`where` 条件筛选；`union` 联合查询，合并两条 select 结果
+ information_schema：MySQL 自带的信息数据库，存放所有库名、表名、字段名（注入拿信息核心）
2. 闭合符号
+ 单引号 `'`：字符型注入最常用，用来闭合原有 SQL 的引号
+ 双引号 `"`：少数场景用
+ 括号 `)`：部分注入需要闭合括号
3. 注释符号（干掉后面多余代码，防止语法错误）
+ `#`：MySQL 单行注释
+ `-- `：-- 后面**必须带空格**，单行注释

> 注释就是告诉数据库 “后面的内容不要执行”，用来吃掉后端代码残留的引号。
>

## 三、注入的分类
### 1. 数字型注入
输入不加引号包裹，一般是 id 这类数字参数。  
Payload 示例：`?id=1 or 1=1`

> 不需要单引号，因为后端 SQL 语句`where id=1`，id 是数字，直接写 or 条件就能修改逻辑。
>

### 2. 字符型注入（最常见，Pikachu 重点）
输入被单引号包裹，必须用`'`闭合。  
Payload：`' or 1=1 #`

> 如果直接输入`or 1=1`，会被当成字符串里面普通文字，不会生效。必须先用`'`把前面的引号关掉，才能写 SQL 逻辑。
>

### 3. 搜索型注入
SQL 结构一般是 `where name like '%用户输入%'`  
闭合 payload：`%' or 1=1 #`

> 前后自带百分号，所以 payload 开头加`%'`来闭合前面的`%'`。
>

### 4. Union 联合查询注入
用`union select`，把第二条查询的结果和第一条合并，**用来回显数据库内容**。  
前提：前后两条 select 查询的**列数量必须一致**。  
步骤：

1. order by 判断字段数量：`' order by 1#` 不断增加数字，报错时就知道总列数
2. union select 1,2 看页面哪几个位置可以回显数据（回显位）
3. 在回显位填入函数，查询库名、版本、用户  
示例：

```plain
' union select database(),user() #
```

+ `database()`：当前正在使用的数据库名字
+ `user()`：数据库登录账号
+ `version()`：MySQL 版本号

> union 就是借用页面原本的输出位置，把我想要查的内容打印在网页上。适合页面会直接输出查询结果的场景。
>

### 5. 报错注入
页面不返回查询数据，但是会输出 MySQL 的错误信息。  
利用`updatexml()`、`extractvalue()`这类函数，把想要查询的数据放进报错信息里，页面报错就带出数据。

> 不能直接回显数据，那就**让报错信息帮我们带出数据**。
>

### 6. 盲注（布尔盲注 + 时间盲注）
页面**没有数据回显，也没有报错**，只能依靠页面变化判断。

1. 布尔盲注：输入不同 payload，页面出现 “正常 / 不存在” 两种不同状态。逐字符猜库名、表名。
2. 时间盲注：页面完全看不出差别，用`sleep(5)`，看网页加载是否延迟 5 秒，判断条件真假。

> 盲注没有直接结果，只能像做判断题一样，一点点猜，速度慢，但适用场景广。
>

### 7. Http 头注入（Cookie/UA/Referer 注入）
注入点不在 URL 参数，在 HTTP 请求头里面。网站直接读取 Cookie、User-Agent 拼入 SQL。

> 不一定只有 URL 里的参数能注入，只要是用户可控、后端直接拿来拼 SQL 的地方，都可能存在注入。
>

## 四、通用注入测试流程（个人总结，实操固定步骤）
1. 判断是否存在注入点：  
字符型：输入单引号`'`，观察页面是否报错；  
再测试 `' and 1=1#`（页面正常）、`' and 1=2#`（页面异常），证明可控输入可以修改 SQL 逻辑。
2. 判断闭合方式：单引号 / 双引号 / 括号
3. order by 判断查询字段数量
4. 找回显位（union 注入）
5. 爆库名 → 爆表名 → 爆字段名
6. 读取敏感数据（账号密码）

>  不要上来直接抄 payload，先判断环境。注入本质是**猜后端 SQL 长什么样**，一步一步试出来。
>

## 五、常见过滤与简单绕过
网站会过滤关键词，简单绕过手段：

1. 过滤空格：用`/**/`代替空格  
`'/**/or/**/1=1#`
2. 过滤 or/union：大小写绕过、双写绕过  
例：`UNIunionON`，过滤 union 时，删除中间 union，剩下 UNION

> 绕过不是万能的，只是防御写的不够严谨。如果用预编译，这些绕过全部失效。
>

## 六、SQL 注入防御手段
1. **预编译（PDO）—— 最优方案**  
SQL 语句结构提前固定，用户输入只作为参数，永远不会当成 SQL 代码执行，从根源杜绝注入。
2. 输入过滤、特殊符号转义：过滤`' # and or union`等关键字
3. 最小权限原则：网站使用的数据库账号不要给 root 最高权限，就算被注入，危害降低
4. 关闭 MySQL 详细报错信息，防止泄露数据库结构

> 过滤和转义很容易被绕过，**预编译才是治本方案**。
>

### 解题步骤
1. **判断注入点**：输入 `'`，页面 SQL 报错，判断是**单引号闭合的字符型注入**。
2. **验证漏洞**：输入 payload `' or 1=1 #`，成功查询出全部用户信息，漏洞生效。
3. **order by 猜列数**：依次测试，得出查询结果共 2 列。
4. **Union 找回显位**：`' union select 1,2 #`，确定 UID、邮箱两处为回显位置。
5. **获取数据库信息**
    - 查库名：`' union select database(),user() #`
    - 爆表名：`' union select table_name,2 from information_schema.tables where table_schema=database() #`
    - 爆字段：`' union select column_name,2 from information_schema.columns where table_name='users' #`
6. **读取账号密码**：`' union select username,password from users #`，拿到 users 表数据。
